# TriAttention 私有 KV 直拷与非整齐 V3 分段选择

[English](triattention-private-copy-and-v3-selection-20261023.md) | 简体中文 |
[优化记录索引](README.zh.md)

日期：2026-10-23。范围：固定 Qwen3.5-35B-A3B BF16、TP=2、两张 Ascend
910B2 宿主上的 0.11.0 源码实现。这是按日期保存的工程观察，不能外推到其他
模型或宿主。

## 实现改动

此前 TriAttention 将逻辑 token 位置映射到物理缓存槽位时分别执行除法、取余、
索引和乘法。新的 Triton 算子在一次 NPU 启动中完成映射。对于私有目标块，
另一算子在一次启动中直接搬运 K 和 V；它支持 Qwen3.5 每 rank 一个本地 KV 头
时连续或带页填充的布局，其他布局仍使用持久工作区。调度器和 provider 在提交
压缩事务前仍要求源块与目标块不相交。

V3 token 选择现在将长度不齐的中间上下文分段合并执行 TopK。分段补齐位置不会
进入选择结果；各段仍使用精确的比例配额，返回的 token 位置有序。零宽度或
零配额分段继续使用逐段路径，按形状生成的索引计划可跨事务复用。实际 SWE 压缩
长度包括 9,605、17,090 和 46,473 token，此前均不能命中等宽批量快路径。
SWE 配对比较器还会识别各组不同的 `VLLM_HUST_EXT_CONFIG` 路径，并继续拒绝
其他启动参数变化。

完整源码测试 216 项通过，Ascend 内核 smoke 通过；上述三种不齐长度的 NPU
选择结果与逐段参考实现完全一致。单卡微基准中，V3 选择由约 3.25 ms 降至
0.49 ms（这三种长度约 6.6–6.7 倍）。搬运 4,608 个 token 时，生产直拷在
连续 K/V 上为 0.117 ms，在带页填充的 K/V 上为 0.112 ms；单层工作区路径
为 0.299 ms。这些只是**独立算子测量**，不能当作服务吞吐提升。

## SWE 匹配服务测量

按[SWE 测试规程](../benchmark/frontier-benchmarking.zh.md)，两侧固定模型
revision、校准统计、准备好的负载、宿主提交、C4 客户端、APC、真实 MTP2、
异步调度、`mamba_cache_mode=align` 和 `FULL_AND_PIECEWISE` 图模式。
每组分别冷启动，通过有效的 60 秒预检和 900 秒窗口，失败请求均为 0。
配置上下文为 262,144 token，实际最长 prompt 为 52,505 token。B0 加载
插件但关闭压缩；B1 均采用 1,024-token 重算窗口、stride 2 和 2,048-token
请求输出门槛。由于中途加入了非整齐 V3 选择，两份源码 cohort 分开列出。

| 第一份，B0 | 262656 | — | 73.916 | 47.546 | 1641 | 217 |
| 第一份，B1 | 4608 | 512 | 72.137（−2.41%） | 47.669（+0.26%） | 1660（+1.18%） | 218 |

百分比均相对于同份源码的 B0。16,128-token 候选在正式窗口内提交 13 次压缩，
每次均收到两个 TP rank 各一次回执。另有四项确定性 32K 检索请求输出正确
代码并触发四次压缩。这项有限检查不能代表 SWE 答案质量。

宽预算候选是本次测得唯一两项目标指标都高于 B0 的 0.11 候选，但单组 900 秒
配对的增幅均低于 0.2%，TTFT P95 还变差 14.27%。跨次运行波动大于这两项
微小增幅，因此**不能据此宣称服务加速可重复**。调整预算也会改变触发时机和
保留的 KV 长度，不能将服务差值全部归因于算子。此结果不是官网榜单提交。

## 与 0.10.0 的对照及端到端分析

[0.10.0 配对证据](../results/evidence/kvcompress-qwen35-20261017-v010-swe-pair.json)
中，所选 4,608-token 候选相对 B0 的每卡输出和解码 P90 分别提高 1.33% 和
1.62%，TTFT P95 增加 8.65%；本次所选 16,128-token 候选对应为 +0.17%、
+0.13% 和 +14.27%。直接比较两个版本的所选 B1，本次每卡输出低 2.28%，
解码 P90 低 1.90%，TTFT P95 高 12.08%。两次测量分别使用物理 NPU 4/5
和 0/2；本次 B0 每卡输出也低 1.14%。因此，跨版本绝对差值不能单独归因于
这次源码修改。

算子加速覆盖的服务工作量有限：所选 B1 在 900 秒正式窗口只提交 13 次压缩，
而 0.10.0 所选 B1 提交 20 次。V3 选择的独立测量每次约节省 2.76 ms；即使
将其直接乘以本次 13 次提交，也只得到约 36 ms 的量级。直拷的 0.117 ms
测量仅针对 4,608-token、单层 K/V 搬运，不能按该数值推断 16,128-token
候选的完整压缩事务耗时，更不能推断 900 秒吞吐。16,128-token 预算还会改变
压缩触发时机，并使压缩后的注意力保留比 4,608-token 配置更长的 KV；这些
持续发生的工作不在选择与直拷微基准中。

将非整齐 V3 cohort 的 B0、所选 B1 原始请求按 play、trajectory ID 和轮次
配对，220 个请求全部匹配。其中 13 个同时满足 prompt 至少 17,152 token
及请求输出上限至少 2,048 token，均属于压缩适用范围；B1 在其中 11 个请求上
的 TTFT 更慢，配对差值平均 +174 ms、中位 +34 ms。其余 207 个请求的平均
配对差值为 −5 ms。适用请求的 TTFT 退化与尾部指标变化方向一致，但 13 个
样本中有较大异常值，不能仅凭平均值断言退化幅度可重复。实现会限制这些请求
的前缀缓存命中，以保留 1,024-token 查询后缀用于重算，并在提交时执行选择、
K/V 搬运及调度事务。这些步骤可能抵消局部算子收益；现有报告没有各阶段耗时，
无法确定每一步的贡献。

本次对照支持“算子更快，但服务加速未得到验证”的结论。确定主因需要在相同
物理 NPU 上固定 KV 预算和请求序列，分别记录前缀重算、完整压缩事务、调度
等待与解码阶段耗时，并重复配对测量。
